## One-liner

We give small education nonprofits free tools that save them hours on admin. In return, we surface what they're actually accomplishing to donors who want to fund local programs but can't find ones they trust.

---

## What we're building

Understory Commons is an admin-automation tool plus donor-facing transparency layer for small, **independent** community-based youth education nonprofits ("CBOs"). Target users: church-hosted tutoring, community center after-school programs, faith-based literacy ministries, independent nonprofits — typically 10–50 students, 1–3 paid staff, volunteer-assisted. Explicitly **not** school-affiliated and **not** federally funded (no 21st CCLC). Underserved by both compliance tooling (priced for federal grantees) and donor CRMs (priced for $1M+ orgs). The product has two surfaces:

- **Coordinator surface** — a free, AI-assisted admin automation tool for program staff. It does the unglamorous work that currently eats hours, falls through the cracks, or doesn't happen at all because there's no staff capacity for it. Primary admin targets, in rough priority order:
  - Attendance capture (the #1 ask from early CBO interviews — current state is no method, no weekly numbers)
  - Permission and release form collection (especially for programs producing student work)
  - Timesheet aggregation and monthly facilitator payroll prep
  - Family / parent communication (today: largely absent because comms infrastructure has lapsed)
  - Progress check-ins on project-based programs
  - Photo and testimonial intake
  - End-of-year program satisfaction surveys (today: chronic non-response on online surveys)

  Verified program data — attendance, activities, outcomes, milestones — is generated as a byproduct of automating these tasks. Coordinators never log data for its own sake.

- **Donor / network surface** — a transparency layer that surfaces aggregated, verified impact metrics derived from coordinator-surface activity. Donors see live program data, not annual self-reported summaries.

The differentiator is that **impact data is a byproduct of admin work the tool does for the coordinator**, not a reporting burden it adds on top. The network is the reason to join; the tool is the reason to stay. Both must deliver independently — if the coordinator wouldn't keep using the tool with no donor traffic at all, the tool is wrong.

Test for any new feature: "does this remove a thing the coordinator currently does by hand, or is currently failing to do?" If no, it doesn't ship in V1, regardless of how good it would look on the donor surface.

## Core invariants — do not break these without escalating

1. **Verification chain integrity.** Every donor-facing metric must trace back to a specific coordinator-surface event with a timestamp, an actor, and a non-repudiable record. No metric is allowed to exist that wasn't generated by real coordinator activity. If aggregation code bypasses this, stop and escalate.

2. **PII minimization (V1 is PII-light by design).** The product handles operational data — session counts, attendance, activity types, outcome indicators — not student or parent identity. We do not store parent contact information, and we do not deliver communications. The tool *generates* draft text (parent updates, weekly summaries, social posts, grant report sections); the coordinator copies it into their existing channel (group text, email, Facebook group, etc.). For attendance, students are referenced by whatever lightweight identifier the coordinator or facilitator uses in the moment — usually first name, sometimes first + last initial, occasionally a nickname. `Participant` has a single `display_name` string field in V1; no structured first/last name split. A structured name is a future migration, not a V1 field. FERPA technically does not apply to non-school-affiliated CBOs, but we operate as though minimizing PII is a hard product constraint anyway. Any change that introduces PII storage or message delivery requires Opus-tier review and an architectural decision record.

3. **Append-only event log.** Coordinator activity is an event stream, not mutable state. Outcomes derive from events. Do not introduce mutations to historical records without an explicit audit trail and a `supersedes_event_id` link.

4. **Idempotency on inbound channels.** Anything that can fire twice (form re-submits, retried syncs, donor-side polling, future webhook integrations) must be idempotent at the application layer.

5. **Workflow fit beats schema elegance.** The right data model is the one that matches how coordinators and facilitators actually work in the moment — not the one that looks cleanest in a schema review. When implementation drifts toward normalization, structured fields, or upfront UI the user won't encounter naturally, treat that as a smell and push back. This applies to Sonnet during implementation — if a Sonnet pass produces a schema-elegant solution that doesn't match real workflow, stop and correct it.

## Tech stack

- **Backend:** Django 5.x, Python 3.12+
- **Coordinator UI:** Django templates + HTMX (no SPA)
- **Donor UI:** Mobile-first PWA, vanilla JS or minimal framework
- **DB:** Postgres in production, SQLite acceptable for local dev
- **AI / LLM calls:** Used for *lightweight* tasks only — attendance parsing from free-text input, draft communication generation, weekly summary generation, grant-report section drafting from captured data. Not used for complex reasoning chains. Cost target: well under $1/program/month.
- **Outbound communication:** Generation only, not delivery. The tool produces draft text the coordinator copies into their own channel. **No Twilio, Mailgun, SendGrid, or equivalent in V1.** Any future delivery integration is a V2 architectural decision, not an incremental feature.
- **Auth:** Magic-link, no passwords. Coordinator creates facilitator accounts (name + email/phone); system sends a one-time magic link. Coordinators see all org programs; facilitators see only their assigned programs. Library choice (likely `django-sesame`) to be confirmed in the Phase 1 plan.
- **Background jobs:** TBD — pick Django-Q2 or RQ before adding a queue, document the choice in `/docs/decisions/`

This is the MVP stack. Do not introduce new infrastructure (Redis, Kafka, K8s, microservices, separate frontend frameworks) without an architectural decision record committed to `/docs/decisions/<date>-<topic>.md`.

## Scope discipline — what is and isn't in V1

The product thesis is still in pre-interview validation. Build in a way that supports iteration based on fieldwork findings, and don't lock in features whose value depends on validation results we don't yet have.

**In scope for V1:**
- Coordinator-surface admin automation for the priority list above
- Lightweight AI assistance (parsing, summarization, drafting)
- Donor-facing program profile with verified operational metrics
- CSV / PDF exports of program data for funders and grant reporting

**Out of scope for V1, even if tempting:**
- Message delivery of any kind (parent comms, volunteer comms, donor comms) — generation only
- Donation routing and the 3–5% transparent operational fee — comes after profiles and metrics are real
- Grant *proposal* writing (crowded, solved category — Grantboost / Grantable / Instrumentl); grant *reporting* from captured data is fair game
- Any feature that primarily benefits the donor surface at the cost of coordinator workflow
- Any feature that depends on a specific funder's reporting format until ≥3 CBOs have asked for it
- Real-time analytics, dashboards, or anything pitched as "insights"

When in doubt, push features down the road. A smaller V1 that one CBO actually uses on Monday morning beats a larger V1 nobody adopts.

## Model routing

**Default model: Sonnet 4.6.** Use this unless one of the escalation conditions below applies.

### Escalate to Opus for:
- Schema or data-model changes that touch more than one table
- Any change modifying the verification chain or the PII-minimization posture
- Debugging where one Sonnet pass has not produced a hypothesis that matches the symptom
- New integration design (donor auth, donation routing, future delivery integration)
- LLM prompt design for new AI-assisted features (the prompt is the contract — get it right before scaling calls)
- Cross-cutting refactors that span the coordinator/donor split

### Never escalate to Opus for:
- Reading files, grepping, exploring the repo
- Scaffolding new Django apps, models, views, urls
- Writing or extending tests against existing patterns
- Template work (HTMX partials, donor PWA views)
- Form definitions, validators, serializers
- Migrations (unless schema design is itself in flux — that's an escalation)
- Renames, simple refactors, lint fixes
- Glue code, env config, deployment scripts

### Plan-then-build separation
For any feature larger than a single endpoint:
1. Open a planning session (Opus). Output a plan committed to `/docs/plans/<phase>-<feature>.md`.
2. Switch to Sonnet for implementation against the plan.
3. If implementation reveals the plan is wrong, stop, update the plan, don't paper over it.

## Workflow conventions

### Sub-agents
Use sub-agents for any task that needs to read a lot of code or external context but only needs to return a summary. Examples:
- "Read the current schema and propose a participant aliasing scheme"
- "Audit all donor-surface views for PII leak paths"
- "Survey background-job library options against our needs"

The parent session stays lean. The sub-agent reads, then returns a written summary.

### Phase discipline
Work in discrete phases. Each phase ends with:
- All commits pushed
- A handoff note in `/docs/handoffs/<date>-<phase>.md` summarizing what shipped, what's deferred, what's broken
- `/clear` to start the next phase fresh, with the handoff note as initial context

Do not let a single Claude Code session span phases. Context bloat is the dominant cost driver — more sessions with less context per session beats fewer fatter sessions.

### Commits
- Conventional Commits format (`feat:`, `fix:`, `chore:`, `docs:`, `test:`, `refactor:`)
- Commit per logical unit, not per session
- If a session ends mid-feature, commit the WIP with a `wip:` prefix and a TODO in the message body

## Code conventions

- Python 3.12+, type hints on all new functions
- `ruff` for lint, `black` for format, both run pre-commit
- Tests required for any code touching the verification chain or the PII boundary
- Tests on coordinator-surface CRUD: nice-to-have for MVP, required by phase 3
- No `print()` debugging left in committed code; use `logging`
- Synthetic test data only — no real participant identifiers in fixtures, ever

## Things to ask before assuming

If any of these are unclear, ask in chat rather than guessing in code:
- Whether donor authentication exists yet (current default: no, browse-only public surface)
- Whether a given metric is allowed to be shown publicly (verification chain check)
- Whether test data is real or synthetic (always synthetic in this repo)

- Whether a "small" change actually crosses the coordinator/donor boundary

## Outcome over architecture

Every slice must end with a thing a real CBO coordinator could use
or a real funder could see. If a slice's deliverable is "schema X
is now reproducible" or "adapter pattern Y is generalizable" with
no user-visible output, the slice is misscoped. Rescope.

Test for any proposed work: "what does a coordinator at a 30-student
DC tutoring nonprofit do with this on Monday morning?" If the answer
is "nothing yet, but in slice N+2 they will" — the work is too far
upstream. Pull it forward or defer it.

## Minimum-viable-grant-data principle

For grant ingest specifically: we are not building a research-grade
ML corpus. We are building a tool that surfaces currently-open,
relevant grants to small DMV youth-ed CBOs. Every ingest decision
serves that goal directly. Tier B/C extraction is not deferred
"because Component 2 will handle it" — it's done at ingest with
deterministic rules wherever the field is deterministically
extractable. Component 2 exists for fields that genuinely require
semantic understanding (eligibility prose, mission alignment), not
for fields where Component 2 is shorthand for "I don't want to
think about it now."

## No new abstractions without a second use case

Shared base classes, plugin systems, generic adapters, and similar
generalizations land in the codebase only after a concrete second
use case has appeared. The first instance is a script. The second
instance might justify abstraction. Three is when the abstraction
is real. Premature generalization is the dominant failure mode
of this kind of work; resist it.

## The fieldwork test for any planning session

Before approving any plan that takes more than one session to
implement: write one paragraph describing what a real DMV
coordinator (Matthew Ratz at Passion for Learning is the reference
persona) does differently after this work ships. If that paragraph
is hard to write, the work is wrong-shaped. Either the plan is too
infrastructural, or it should be three smaller plans where each
one passes this test.

## Honest assistant behavior

The assistant should push back when a request would produce
elaborate work that doesn't move the user closer to a fieldworkable
artifact. "Build the eval harness for the retrieval model" is real
ML work, but if no retrieval model exists yet and no opportunities
need ranking yet, it's premature. Flag this, propose the smaller
thing that would actually be used now, and let the user decide
whether to overrule.
